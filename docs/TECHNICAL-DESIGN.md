# Triad: Klondike — Launch Technical Design (v1.1)

This document is the implementation contract behind `RULES.md`. It is English-only,
is not player-facing, and does not become a second rulebook. Its job is to define the
authority, persistence, failure handling, and engine integration needed to make the
observable rules reliable in Arma Reforger.

The launch target is deliberately small. Prefer one clear state machine and one safe
server command over several overlapping frameworks. A mechanism not required by
`RULES.md` or by an invariant below is out of scope.

## 1. Contract and Source Order

When sources disagree, use this order:

1. `RULES.md` defines player-observable behaviour and the launch boundary.
2. This document defines the implementation that preserves that behaviour.
3. The validated server configuration supplies mutable values and authored world data.
4. The live in-game interface displays the effective configuration and authoritative
   state.
5. Generated PDFs explain the game but never own mutable values.

An implementation shortcut may not silently change a rule. A design change first
updates `RULES.md`, then this document, the configuration schema, player UI, tests, and
both generated PDFs where applicable.

Terms used here:

- **Vakhta** — one persistent campaign between full wipes.
- **week** — one configured leaderboard and carryover interval within a Vakhta.
- **regular faction** — Meridian, Granit, or Locals.
- **backend identity** — the stable server identity used across connections; never a
  transient player or replication id.
- **operation id** — a high-entropy request id generated by the authenticated client
  before a player/cockpit command, or a deterministic server id for a scheduled job;
  the server binds it to actor, command type, and canonical payload.
- **world entity** — a replicated Enfusion entity such as a character, item, vehicle,
  corpse, or structure.
- **logical record** — server state such as a wallet, bid, registration, or lease.
- **local backend** — the service on the game server's machine that is the system of
  record for every logical record. The game calls it over the loopback interface; it
  never pushes, and it never listens on a public interface.

## 2. Runtime Architecture and Authority

### 2.1 Server boundary

The dedicated server is authoritative for every gameplay decision. Clients may request
an action and predict presentation, but never choose its result. In particular, the
client never supplies a trusted price, faction, quantity, mine yield, capture result,
storage capacity, access-list decision, auction rank, timer expiry, or entitlement.

Every mutation enters through a typed domain command. A command contains:

- the authenticated actor and, where different, the subject;
- an operation id;
- the target's stable id;
- an expected record revision where concurrent edits are possible;
- only the player choice that cannot be derived on the server;
- the relevant configuration revision;
- an operator reason and permission context for cockpit commands.

The server returns a typed success result or a stable refusal reason. Retrying an
accepted operation returns its recorded result rather than applying it again. Stale
record or configuration revisions cause a refresh and retry, not a best-effort write.

### 2.2 Domain services

Keep ownership of state explicit. The launch implementation needs these cohesive
services, even if several live on one game-mode component initially:

| Service | Owns |
|---|---|
| Vakhta and calendar | Vakhta id, week ids, boundaries, rollover and wipe jobs |
| identity and faction | audited UUID readiness, faction membership, projected-roster admission, transient invitations, Garrison whitelist and the whitelisted identity's second (Garrison) character, active-character selection, starter loadout/cutter issuance, spawn eligibility |
| wallet and ledger | available money, auction reservations, append-only money entries |
| markets and recovery | quotes, sales, purchases, receipts, odd jobs |
| weekly results | accepted crystal-sale rows, personal totals, faction aggregate, carryover |
| world registry | stable authored ids and bindings for zones, mines, faces, traders, garages, plots, and routes |
| mines and cutting | ownership, capture, per-player face cooldowns, Local alarms and activity |
| safe zone and aggression | target/source-side protection, Aggressor state and service restrictions |
| reconnect | clean logout, retained bodies, reconnect possession, expiry |
| secure storage | the single per-player item pool, logical capacity and overflow |
| vehicles | registrations, deployments, ACLs, return, loss, cargo finalization |
| plots | lease entitlement, authored shell/socket bindings, installed Storage Expansion and its shared-pool bonus |
| auction | lots, sealed bids, escrow, ordering, settlement and refunds |
| naming | approved candidates and next-Vakhta map-name assignments |
| cockpit | role-checked queries and invariant-preserving operator commands |
| persistence and recovery | schemas, checkpoints, operation recovery, reconciliation and backups |
| audit and telemetry | append-only operator/security events and operational health |

There is no faction-economy service, item-provenance service, dynamic market, general
quest framework, vehicle-insurance framework, or separate prestige currency.

Every service that owns logical records is backed by the local backend. The game-side
service validates what only the game can see, sends one typed command, and applies the
physical effect after acceptance (section 4.2). Reconnect, safe zone and aggression,
mines and cutting, and world registry are game-side services over the physical world.

### 2.3 Stable identities and revisions

Use stable, namespaced ids for players, Vakhtas, weeks, mines, working faces, safe
zones, trader channels, garages, plots, auction lots, vehicle registrations,
deployments, storage pools, plot-module installations, and operations. Runtime entity ids and array
positions are not persistent identities.

A player's backend UUID is usable only on the server and only after that connection's
audit-success event. Before then, or if the dedicated-server backend returns a null or
empty UUID, every identity-keyed query or mutation fails with a retryable
`IdentityNotReady` result. In particular, do not lazily create a wallet, faction
registration, starter grant, storage pool, bid, vehicle registration, plot right,
receipt, or cockpit role from a connection id, display name, or client-supplied value.
Reconnect and concurrent join paths converge on the same audited UUID before loading or
creating player state.

Every mutable logical aggregate has a monotonically increasing revision. Commands that
can race—bids, wallet spending, storage sessions, vehicle deployment, ACL edits, plot
module installation, and cockpit corrections—compare the expected revision before
mutation.

### 2.4 Time

The server uses one configured civil calendar for published Vakhta and week boundaries.
Persist expiries as UTC deadlines, not remaining durations or monotonic-clock values.
Use a monotonic clock only for elapsed-time calculation inside one running process. This
prevents restart from extending an Aggressor marker, alarm, cooldown, auction, lease,
Garrison-island grace, retained-body deadline, or cleanup lifetime.

Calendar ids are calculated once and stored on committed events. A later clock or time
zone correction must not move an existing sale or bid into a different interval.

### 2.5 Chosen launch topology

The launch architecture is not substrate-neutral:

1. the dedicated game server owns all live gameplay authority;
2. the local backend stores every logical record and answers every consequential
   command over the loopback interface;
3. Reforger's native `PersistenceSystem` stores the physical world and the stable ids
   that link it to backend records;
4. the launch cockpit is an in-game admin UI over owner-to-server RPCs;
5. a narrow custom RCON namespace exposes emergency and automation commands; and
6. an external host service manager owns process restart, cold backups, restore, logs,
   and deployment of both the game server and the local backend.

`$profile` JSON may hold server configuration. A website synchronises with the local
backend, never with the game, and is read-only with respect to the game. Neither is a
second source of truth for wallets, bids, leases, registrations, results, or world
state. The game script exposes no inbound HTTP server; the game is always the caller,
and when the local backend does not answer, consequential commands are refused
(section 4.2) while ordinary play continues.

## 3. Configuration Contract

All balance, schedule, capacity, catalog, eligibility, placement, and retention values
are server configuration. Do not embed them in scripts, prefabs that cannot be audited,
localization strings, HTML, or PDFs.

The versioned configuration must cover at least:

- Vakhta dates, time zone, week schedule, rollover windows, maintenance policy, and wipe
  policy;
- regular-faction admission policy, the corporate maximum roster lead, the Local
  maximum share (launch default `20%`), invitation lifetime/cooldown, Garrison whitelist
  integration, starter loadout and cutter definitions, and spawn definitions;
- safe-zone shapes, Aggressor duration and triggers, the minimum accepted collision
  damage for collision-caused Aggressor status, service restrictions, Garrison-island
  warning grace, retained-body base duration (launch default five minutes), and corpse/
  retained-body behaviour;
- enabled mines, capture zones and rates, decay, working faces, cutting duration,
  cutter eligibility, yield, personal face cooldown, Local alarm lifetime and
  notification throttle, and delayed activity buckets;
- trader access, catalogs, buy and resale prices, crystal-sale rules, recovery-job
  threshold, payout, cooldown, and task definitions, and the single launch cutter price;
- secure-storage base capacity, Storage Expansion bonuses, item eligibility, and
  session limits;
- garage catalogs, vehicle prices, deployed limit, restoration fee, return checks,
  authored deployment areas, footprint/terrain/clearance rules, owner-marker policy,
  abandonment policy, and public cargo-crate lifetime;
- plot activation, authored permanent shell/console/socket bindings, city/faction
  eligibility, personal and optional Kamensk faction limits, term schedule, the one
  launch Storage Expansion definition, its direct personal-money price and capacity
  bonus, and lease-loss module compensation;
- auction schedules, minimum bids, eligibility, lot definitions, and naming targets;
- checkpoint interval, backend answer-time limit, readiness re-check interval,
  receipt/audit retention, backup schedule,
  replication page sizes, cockpit role assignments, and the RCON command allowlist.

Authored world records use stable ids and explicit activation flags. Mine count, face
count, plot count, and exact placements therefore change through data rather than
branches in code.

### 3.1 Validation

Startup rejects an invalid configuration before gameplay opens. Validation includes:

- unique stable ids and valid entity bindings;
- complete references between terminals, plots, garages, mines, faces, zones, and lots;
- non-overlapping or otherwise unambiguous plot regions, and exactly one permanent
  non-destructible shell, management console, and Storage Expansion socket for every
  enabled plot, with authored service/road/garage clearance;
- valid schedules and non-negative durations/capacities/prices;
- a corporate maximum roster lead of at least one, a Local maximum share in the valid
  percentage range, and projected-admission arithmetic that permits no bootstrap
  exception;
- trader relationships that cannot create immediate NPC buy-resell profit;
- a recovery threshold at or above the full NPC price of the single launch cutter,
  with a positive payout and finite cooldown so repeated eligible work cannot dead-end
  before that cutter is affordable;
- a positive retained-body base duration and a reconnect/body rule that cannot shorten
  an existing Aggressor consequence;
- non-negative collision-Aggressor damage threshold and Garrison-island warning grace;
- valid auction close times, lease slots, naming targets, and candidate moderation state;
- a deployed-vehicle limit compatible with the configured garage catalog, and each
  enabled garage's deployment area able to contain every allowed vehicle footprint;
- a secure-storage physical representation able to hold the greatest configured
  logical entitlement plus existing overflow during a configuration decrease.

World placement still requires the playable route checks in `RULES.md`; coordinate
validation alone cannot prove encounter flow.

### 3.2 Applying changes

Each accepted configuration change records actor, reason, old revision, new revision,
diff, validation result, and effective time. The cockpit previews the affected systems
before activation.

Committed transactions and closed intervals retain their configuration snapshot.
Long-running operations store the fields that must remain stable until completion.
Examples include an extraction cycle's output, an auction lot's terms, a plot's lease
term, and an installed Storage Expansion's paid cost. A request created against a stale
quote or revision is rejected with a refresh reason; completed history is never
recalculated.

Capacity-style limits are admission rules, not retroactive deletion rules. If the
deployed-vehicle cap falls below an owner's current functional count, those deployments
remain until return, loss, or wipe and no command may increase the count while it is at
or above the new cap. If a personal or Kamensk plot cap falls below active or already-
settled future leases, those grants remain through their awarded terms; new bid
admission uses projected post-transition holdings under the new cap, so excess rights
cannot be renewed or expanded. A configuration change never silently destroys live
property.

The same rule applies to faction balance. Lowering the corporate maximum lead or Local
maximum share never moves or evicts an assigned identity. It only refuses an initial
selection or regular-faction change whose projected current-Vakhta roster remains
illegal. A Storage Expansion price change never rewrites an installed module's exact
paid-cost record; capacity changes apply as entitlement changes and use ordinary
withdrawal-only overflow rather than deleting items.

## 4. Persistence, Transactions, and Recovery

Two stores, one fixed split. The local backend is the system of record for the logical
records in section 4.1; it keeps them durably across its own restarts and answers every
consequential command with accepted, refused with a stable reason, or already applied.
Native Reforger persistence stores the physical world only: characters, vehicles,
structures, storages, items and their child graphs, plus the stable ids that link them
to backend records. No fact is owned by both stores; the linking id is the only thing
they share.

One checkpoint coordinator owns every automatic, cockpit-requested, shutdown, and
lifecycle save of the physical world. `SaveGameManager.RequestSavePoint` is a
whole-world operation, so the coordinator never starts one per low-level state change,
never allows overlapping saves, prevents a save from capturing the middle of a physical
transition, and publishes the last successful save id/time, save duration and failures
to the cockpit. It does not gate consequential commands; the local backend does.

Do not treat `PersistenceSystem.Save()` as durable by itself: it only stages data until
the storage is flushed. Do not call `CommitStorage()` ad hoc as a transaction primitive;
the engine explicitly warns that misuse can create inconsistent save points. `$profile`
file writes have no proven atomic rename, fsync, or cross-record transaction and are
never a store for money, contracts, or audit.

### 4.1 Durable records

Every record begins with a schema version and supports explicit migration. The records
below live in the local backend, except `ReconnectState`, which the game keeps beside
the retained character it describes, and the native storage roots that `SecureStorage`
references. The minimum durable model is:

| Record | Essential data | Lifecycle |
|---|---|---|
| `VakhtaState` | id, dates, active week, config revision, lifecycle-job checkpoint | survives restart; replaced by completed wipe |
| `PlayerState` | backend UUID, regular-faction assignment with its saved-character reference, faction epoch, whitelist flag with the optional saved Garrison-character reference, active character selector, optional Garrison-island trespass expiry, starter-loadout/cutter-issued flags, operational eligibility | Vakhta-scoped except account/admin identity |
| `Wallet` | total, reserved, revision | Vakhta-scoped |
| `LedgerEntry` | operation, reason type, signed amount, balance result, related object, time | append-only until wipe/export policy |
| `CrystalSale` | seller, faction-at-sale, week, quantity, price, proceeds, carryover contribution | immutable until wipe |
| `CarryoverWeek` | player, week, credited amount, configured cap snapshot | Vakhta-scoped; consumed exactly once by wipe |
| `MineState` | owner, capture direction/progress, revision | Vakhta-scoped |
| `FaceCooldown` | player, face, absolute expiry | Vakhta-scoped |
| `MineIntelState` | alarm owner/expiry, activity samples/publication times | Vakhta-scoped |
| `AggressorState` | player, absolute expiry, last authoritative cause and attribution reference | Vakhta-scoped; absent when unmarked |
| `ReconnectState` | player, character persistence reference, disconnect time, configured-base snapshot, absolute body expiry, Aggressor expiry, seat reference | runtime/restart recovery as required |
| `SecureStorage` | owner, persistent native storage-root UUID, used capacity, entitlement inputs, revision | Vakhta-scoped |
| `VehicleRegistration` | registration, owner, definition, state, ACL, deployment, revision | Vakhta-scoped |
| `VehicleDeployment` | deployment id, registration, persistent entity binding, state and finalization ids | until return/loss reconciliation |
| `PlotState` | plot, current/future lease, optional Storage Expansion installation with exact paid cost, capacity entitlement, revision | Vakhta-scoped |
| `AuctionLot` | adapter, terms snapshot, state, close, settlement operation, revision | Vakhta-scoped |
| `AuctionBid` | bidder, exact amount, reservation, accepted sequence, revision/status | until settlement/refund and audit retention |
| `NamingAssignment` | target, approved name, source lot, apply Vakhta, applied flag | survives only the bridging wipe |
| `OperationRecord` | id, type, stage, request/result, affected revisions | until recovery and audit retention |
| `AuditEntry` | actor, permission, reason, before/after references, outcome, correlation id, time | operational retention across wipes |

World items, characters, vehicles, corpses, and structures use engine persistence where
it preserves the required identity. Logical records never rely on a replicated entity
existing at the moment they are loaded.

### 4.2 Commit model

Within a running server, each typed command is validated on the main thread before it
leaves the game: identity readiness, permission, expected revisions, configuration
revision, and the physical item/entity state the backend cannot see. The command then
goes to the local backend as one call carrying the fields of section 2.1. The backend
applies it atomically against its records and answers accepted with the result and a
receipt, refused with a stable reason and the current authoritative value, or already
applied with the recorded result. The game applies the physical effect (item creation
or removal, cargo transfer, deployment, possession) only after acceptance, and never on
a late, missing, or malformed answer.

Use that path for NPC sales and purchases, recovery-job completion and payout, direct
money transfers, bid money reservation and settlement, direct Storage Expansion
purchase/removal compensation, registered-vehicle deployment/return/destruction and
cargo finalization, faction change, operator value compensation, and the wipe.

The operation id makes retry safe. When the answer does not arrive within the configured
limit, the player sees a refusal naming the reason and nothing is applied; the same
operation id sent again resolves to accepted, refused, or already applied. A repeated
operation id with a different payload is refused and recorded as a security event. The
game never journals a consequential command for later replay: while the backend is
unreachable or its contract version is unknown, consequential commands are refused and
ordinary play continues.

A physical effect that must follow acceptance and can itself fail (spawning a vehicle,
moving cargo, removing an item) is recorded on the backend record as a stage, and boot
reconciliation (section 4.3) finishes the recorded next stage or applies its documented
compensation by operation id. Recovery never blindly repeats item creation/removal,
cargo transfer, payout, reservation, or deployment.

Cutting and ordinary secure-storage movement use server-main-thread validation,
aggregate revisions, and normal periodic world checkpoints. They do not create a backend
call for every item move. An abrupt process loss may roll these ordinary actions back
to the last successful checkpoint, but the restored world must be one consistent old
snapshot and must not duplicate a live result.

Do not write a numeric answer-time limit, re-check interval, or command rate into this
document before the backend spike (section 19, item 4) measures it on the packaged
mission with the backend running alongside.

### 4.3 Boot sequence and reconciliation

Gameplay remains closed while boot performs:

1. schema and configuration validation;
2. the local backend contract-version check; an unreachable backend or an unknown
   contract version leaves the boundary not ready and boot continues. Readiness is
   re-checked on the configured interval until it recovers; once boot has finished,
   players may enter while consequential commands are refused;
3. unambiguous selection and load of the current Vakhta save point of the physical
   world;
4. recovery, by operation id, of accepted operations whose physical stage is
   incomplete;
5. reconciliation of persisted world entities with backend vehicle registrations,
   retained characters, public cargo crates, secure item graphs, and authored plot-
   module presentation bindings;
6. catch-up of overdue week, auction, lease, alarm, cooldown, and cleanup transitions;
7. invariant checks and a new checkpoint;
8. publication of server-ready state.

Catch-up is deterministic and idempotent. If several boundaries elapsed during an
outage, process them in chronological order while using their stored ids. A missing or
ambiguous destructive-world binding stops the affected aggregate for cockpit review; it
does not guess and create a duplicate.

The exact unattended dedicated-server save-selection/resume configuration is a required
spike. Until it is proven, startup fails closed instead of inventing a save name or
silently starting a fresh Vakhta.

Klondike player-character persistence must not use vanilla's post-load deletion of
characters whose owners fail to reconnect during one short startup timeout. Configure
the player-character entity record with `SelfSpawn = false` and `SelfDelete = false`,
and replace/disable the default `SCR_PlayerReconnectData` unused-character cleanup for
this collection. `PlayerState` retains the audited UUID-to-character reference; the
spawn logic explicitly requests that record when its owner later joins and possesses
the restored character. An authoritative ordinary death explicitly clears the
`PlayerState` reference and retires the dead character record through the death/respawn
workflow; it must not rely on `SelfDelete` to infer that transition. Spikes 7 and 11
must prove a planned restart with several offline saved owners who reconnect only after
the vanilla timeout: every one receives exactly their saved character, inventory,
health and position, with no duplicate world body.

### 4.4 Invariants

Continuously assert and expose violations of these invariants:

- wallet `reserved` is never negative or greater than `total`;
- one operation id has one terminal result;
- one audited UUID has at most one current regular-faction assignment, and transient
  invitations never contribute to projected roster counts;
- one audited UUID has at most one Garrison character, only while it is whitelisted,
  and never more than one live world body across its two characters;
- one vehicle registration has at most one functional deployment;
- a deployment command never increases a player's functional count while that count is
  at or above the effective configured limit; grandfathered excess may only decrease;
- one player has at most one current bid per lot;
- every active bid reservation has one matching wallet reservation;
- a settled/cancelled lot has no unreleased losing reservation;
- a plot has at most one active lease and one selected future lease;
- a plot has at most one installed Storage Expansion, and its capacity bonus is counted
  exactly once only while its owning lease is active;
- secure storage contains no kolguyevite anywhere in its nested item graph;
- overflow never deletes or silently moves an item;
- a destroyed deployment creates at most one cargo crate;
- carryover for a sale and application at wipe occur at most once.

## 5. World Registry, Factions, Characters, and Spawns

### 5.1 Authored world registry

At startup, bind configured stable ids to authored entities for protected zones, faction
quarters, faction and Local spawns, Garrison territory, mines, capture volumes, working
faces, traders, faction-administration services, storage terminals, garages, plots, and
map labels. A garage binding includes its deployment area and validation volumes; a plot
binding includes its permanent shell, sole console and visual socket. Bind by explicit
component/key, not display name, position, or prefab resemblance.

Missing required bindings prevent that system from opening. Optional configured sites
remain disabled cleanly. Map markers and interaction prompts read this same registry.

### 5.2 Faction capabilities

Capabilities are explicit server policies, not scattered faction comparisons:

- Meridian and Granit may move capture and extract only from a mine they own.
- Locals never own or capture, may extract at normal configured yield from every mine,
  receive delayed coarse mine activity, and trigger an owner alarm at controlled mines.
- Garrison membership is separately whitelisted, is the only way to obtain a Garrison
  character, and grants none of the regular progression or cockpit permissions.

Faction balance uses current-Vakhta registrations, not live concurrency. Count each
audited backend UUID with a current regular-faction assignment exactly once, including
offline and inactive players; exclude Garrison. Logging out never frees a place. An
initial selection adds one projected regular registration, while a regular-faction
change moves the existing registration between counts.

For every initial selection or change, atomically calculate the post-command counts:

- a Meridian or Granit target is eligible only when its projected count is no greater
  than the other corporation's projected count plus the configured maximum roster lead;
- a Local target is eligible only when `projectedLocals <= floor(localMaxShare *
  projectedRegularTotal)`. Implement this as integer/rational arithmetic, not a
  floating-point comparison;
- the Local value is a hard maximum, not a target. Its launch default is `20%`, and
  there is no bootstrap exception, so the first Local registration is legal only with
  a projected regular total of at least five; and
- a lower configuration never evicts existing members. A target at or beyond a new
  limit accepts no admission until the projected result is legal again.

Serialize this calculation with membership mutation so two simultaneous requests
cannot consume the same legal place. Return authoritative counts, effective limits and
a stable refusal reason to both the selector and faction-change preview. There is no
automatic reassignment, online-player weighting, inactivity release, population-scaled
economy, or operator-only Local overflow.

The launch friend feature is a lightweight, transient invitation rather than a second
admission policy. An assigned regular player may invite one audited, online player who
is not assigned to Meridian, Granit, the Locals, or Garrison. The server resolves the target
connection to its audited UUID and allows at most one outstanding outgoing invite per
sender and one incoming invite per recipient. On acceptance, request the inviter's
current faction and run the ordinary projected-roster check at that moment. The invite reserves no
place, has no queue, and bypasses no limit. It expires after the configured lifetime
and is discarded on either disconnect, either faction assignment, inviter faction
change, or server restart; sends use the configured cooldown. The existing group-
invitation RPC/UI is only a presentation precedent because vanilla groups require both
players to already share a faction. Store an exact server-issued invitation id with the
two UUIDs and expiry. The owner-targeted acceptance RPC resolves the authenticated
recipient, consumes that id idempotently, honours the target's platform invitation
restriction, and then repeats every admission check; a transient player id or client-
claimed inviter/faction is never authority.

Ugoldar quarters are physically traversable; ordinary services are gated. The sole
cross-faction exception is the `ReturnVehicle` command at the registration's correct
garage for an actor on that vehicle's ACL; it grants no catalog, deploy, restore, or ACL
authority.

Garrison members have no geographical restriction: they may travel and fight anywhere,
subject to the same safe-zone and gameplay rules as everyone else. The Garrison island
restriction applies only to regular factions. On entry, start a server-owned configured
absolute grace deadline and show the boundary warning/countdown; leaving in time
cancels it, and remaining inside at expiry invokes the trusted server kill path. A
retained disconnected body remains subject to the same deadline. Persist the active
deadline and reconcile entry, exit, fast movement, spawn, reconnect, restart, and join-
in-progress on the server so a missed client trigger cannot grant access or restart the
countdown. This territorial freedom does not grant Garrison
mining, regular services, plots, results, carryover, auctions, or cockpit capability.

A whitelisted identity owns two independent character records: the regular one under
every regular rule above, and a Garrison one that exists only while the whitelist flag
is set. The selection screen offers the Garrison entry only to a whitelisted identity.
`PlayerState` stores which character is active; exactly one may have a live world body
at a time. A swap is not a special path: it runs the section 6.3 departure
classification for the character being left (save-and-remove inside a protected city
without Aggressor state, otherwise a retained body with the ordinary deadline) and then
the ordinary spawn or reconnect path for the other character. A swap is refused while
the current character has a pending consequential operation. Whitelist grant is an audited
cockpit command that creates the Garrison record and its zero-balance wallet; whitelist
revocation is an audited resumable job that removes the Garrison character, its carried
equipment, and its wallet, and touches nothing on the regular record. Neither command
runs the regular faction-change job, and the regular character's roster place, property
and results are never affected by either.

### 5.3 Character lifecycle

On the first eligible regular-faction spawn of a Vakhta, issue the configured starter
loadout and one starter cutter. Each is issued once per player identity and Vakhta.
Persist their issued flags before or with item creation so a retry cannot duplicate
either grant. The flags are not reset by death, reconnect, poverty, respawn, or a
regular-faction switch during the same Vakhta.

Initialize that player's seasonal wallet exactly once from the configured opening
balance plus any carryover staged for that identity by the preceding wipe. Lazy
initialization for a player who first connects later in the Vakhta uses the same
idempotent record and cannot claim the opening grant twice.

Initialize the Garrison character's Vakhta-scoped wallet exactly once with a zero
opening balance and no carryover or starter grant; it is a separate wallet from the same
identity's regular wallet. It may then receive ordinary eligible gear-sale proceeds and
player transfers. Reconnect and retry reuse the same wallet, whitelist revocation
removes it, and the full wipe clears it with every other current balance.

Death uses ordinary corpse inventory. Money and secure storage are logical and survive
ordinary death; every carried physical item remains lootable, including the cutter and
kolguyevite. A protected zone prevents non-self player-attributed damage but does not
privatize an existing corpse.

Spawn selection is server-validated:

- Meridian and Granit use their Ugoldar bases;
- Locals choose their Ugoldar or Kamensk spawn on each ordinary respawn;
- Garrison uses its own base;
- plots, mines, and paid forward positions are never spawn sources.

## 6. Safe Zones, Aggressor State, and Disconnects

### 6.1 Protected-city damage

Protection is enforced on the server. Reject every non-self player-attributed damage
event when either the protected target or the authoritative attack source/fire origin
is inside Ugoldar or Kamensk, regardless of faction. A projectile or explosive created
inside remains tagged with its protected origin and cannot damage a target after leaving
the boundary. Remote or delayed damage also carries the controlling player's server
position at the moment of trigger/detonation as an attack source. Capture that position
and controlling identity in the authoritative detonator action; the explosive's arming
instigator alone is insufficient for remote fire. Treat impact caused by a player-driven
vehicle against another protected character, occupied vehicle, or registered vehicle as
player-attributed and reject it. If reliable driver attribution cannot be proven for an
impact path, conservatively reject that impact damage to those protected targets rather
than leave a ramming bypass. This safe-zone veto is intentionally broader than the
collision rule that creates Aggressor state. Cover characters, occupied or registered
vehicles, and authored plot service entities; do not depend on weapon holstering,
disabled UI actions, or a client-claimed position.

Environmental damage, survival damage, genuinely unowned accidents outside the
conservative collision fallback above, and the city's Aggressor execution are not
converted into general immunity. The city execution uses an explicit trusted
damage/kill path that cannot be rejected by the safe-zone filter.

Boundary checks need server-side continuous/trigger reconciliation so a fast-moving
entity, teleport, reconnect, or spawn cannot skip enforcement for a frame long enough
to use a service.

### 6.2 Aggressor aggregate

`AggressorState` is keyed by player identity and stores an absolute expiry and the last
authoritative cause. Mark or extend it when that player:

- fires a weapon, whether or not it hits;
- releases, triggers, or remotely detonates an offensive grenade, explosive, or
  throwable;
- deals accepted positive non-collision player-attributed damage to any other player,
  including a faction ally;
- deals accepted positive non-collision player-attributed damage to another player's
  occupied or registered vehicle; or
- causes accepted positive collision damage meeting the configured collision threshold
  to one of those targets, but only when a collision-specific server sample identifies
  that player as the pilot at the moment of contact.

Do not infer a collision aggressor later from current seat occupancy, vehicle owner,
last driver, nearest player, or the vehicle damage callback alone. If the contact-time
pilot or damage path is ambiguous, mark nobody. A safe-zone collision remains rejected
even when this narrower attribution cannot be proven. The attribution spike must prove
the collision-specific source and applied-damage value before this trigger is enabled;
failure disables collision-caused Aggressor marking, not the protected-city impact veto.

Receiving damage, environmental damage, and self-damage do not mark the victim. Damage
attribution must survive delayed projectiles and explosives; a client RPC declaring
that it fired is insufficient. Returning fire is an offensive action and marks the
defender under the same rules; there is no self-defence exception.

While marked, the server rejects traders, secure-storage access, garage operations,
plot terminals, and clean logout. The UI continuously shows the authoritative absolute
expiry. Death clears the state. Expiry is processed idempotently and naturally passes
during downtime.

Entering a protected city while marked, or becoming marked while already inside one,
causes immediate server-side death. Apply the check both from the zone transition and
from the Aggressor mutation so event ordering cannot open a gap. Services independently
recheck the state as defence in depth.

If the executed character was driving, execution affects the character only. Do not
stop, unlock, confiscate, return, mark Lost, or empty the vehicle. It continues under
ordinary physics; registration ACL, cargo, damage protection and safe-zone rules remain
unchanged. Coasting into a city and later recovering the vehicle/cargo is an accepted
consequence, not a reason to add a special seizure or towing state.

### 6.3 Departure classification

Only a planned server shutdown uses the shutdown path. Every ordinary Quit, network
loss, client crash, and kick uses the same gameplay rule; do not try to infer whether a
disconnect was intentional.

At departure, after resolving a simultaneous death or safe-zone execution:

- inside a protected city with no Aggressor state: save and remove normally;
- every other case: retain the same living character as a killable, lootable world
  entity.

Snapshot the configured retained-body base duration when departure is accepted. Its
launch default is five minutes. The absolute retained-body deadline is
`max(disconnectTime + baseDurationSnapshot, AggressorExpiry)`. A later authoritative
qualifying action attributed to that character may extend the Aggressor expiry and
therefore the body deadline. Store the character binding, base snapshot and absolute
deadline before acknowledging disconnect handling. Do not distinguish Quit, timeout,
network loss, crash, or kick, and do not build a separate combat-disconnect detector.

Reconnect within the deadline possesses the same living entity with the same inventory,
health, position, and vehicle compartment. It does not spawn a copy. If the character
has died, normal death/respawn and corpse rules win. At a live expiry, persist the
character exactly once and then remove it. If it dies during removal, death wins and
the corpse remains. A later reconnect after a successful live expiry loads that same
saved character at its saved health, inventory and position rather than using a faction
spawn or issuing another starter grant.

A corpse in a registered vehicle must remain removable and lootable regardless of
whether the dead player disconnected. The corpse-removal interaction bypasses the
registration ACL only for extracting that dead body; it does not grant vehicle use or
cargo access.

During planned shutdown, stop new mutations, checkpoint all characters normally, and
remove no inventory as a logout penalty. Persist absolute Aggressor state so restart or
elapsed wall time decides whether it remains active. Kolguyevite needs no separate
logout system: it follows the ordinary character inventory through these paths.

## 7. Personal Economy, Markets, Recovery, and Commerce

### 7.1 Wallet and ledger

Each player has one virtual wallet. Represent `total`, `reserved`, and therefore
`spendable = total - reserved`. All debits validate spendable money; auction escrow is
reserved money, not a second currency. Money is not a world item and is not lootable on
death.

Every mutation appends a typed ledger entry with operation id, subject, reason,
related object, signed amount, before/after balance, configuration revision, and time.
Corrections are compensating entries; operators never rewrite or delete a committed
entry.

### 7.2 NPC buyers and catalogs

The server resolves the trader from the authored registry, validates physical access,
faction, Aggressor state, item eligibility, live catalog revision, and inventory
ownership, then calculates the quote. The client sends item selections, not prices.

Required channel policy:

- Meridian, Granit, and Local Ugoldar buyers use the configured safe baseline for
  eligible crystal and ordinary used gear;
- the Local buyer exposes the Local-exclusive purchase catalog without a crystal
  premium;
- Kamensk is available to regular factions and pays the same configured higher price
  to all of them;
- Garrison may use Kamensk only to sell eligible ordinary gear at that gear quote; it
  cannot sell crystal or buy from the regular-faction catalog;
- all NPC buy/resale relationships pass anti-arbitrage validation;
- ordinary gear carries no previous-owner, Garrison, faction, mine, or stolen stamp.

Crystal sale is a dedicated operation over eligible kolguyevite carried by the seller.
Vehicle cargo must first be physically moved to the character if it is not part of the
configured carried-inventory traversal. The transaction removes the chosen quantity,
credits money, commits the weekly result, faction-at-sale aggregate, carryover
contribution, and one receipt exactly once. Assignment to a week uses server commit
time. A boundary race either commits wholly before or wholly after the boundary.

Gear sale uses the same safe item-removal and wallet pattern but never calls weekly
result or carryover code. Selling a container whose nested graph contains kolguyevite
is rejected rather than consuming crystal through the gear-sale path. Loadout refund,
arsenal return, dismantle, and other item-conversion routes use the same recursive
exclusion.

Receipts contain accepted items and quantities, unit prices, total proceeds, resulting
wallet, weekly crystal quantity where applicable, this sale's carryover contribution,
cap progress, and operation id. Refusals return the actual access, item, price,
inventory, configuration, or Aggressor reason.

### 7.3 Purchases and starter replacement

NPC stock is not depleted globally. Purchases debit spendable money and create the
configured item once through the checkpoint-gated value-operation path. Cutter
replacement is an ordinary purchase or player acquisition; no poverty, death, or
reconnect path reissues the cutter from the one-time starter loadout.

### 7.4 Recovery jobs

Recovery work is one city-maintenance state machine, not a general quest engine:

`Eligible -> Accepted -> Completed` or `Cancelled/Expired`.

Eligibility is restricted to regular factions and compares the configured threshold
against wallet `total`, including money currently reserved by bids. It deliberately
ignores equipment, vehicles, plots, and other property. Apply the configured cooldown.
The threshold is at least the full NPC purchase price of the single cutter available at
launch. There are no cutter tiers: validation compares the recovery configuration
directly with that one configured cutter price. A positive
payout and finite cooldown leave an eligible player able to repeat the route until that
cutter is affordable.
The player accepts at an authored provider, receives an ordered route of configured
service points inside the same protected city, and completes the maintenance
interaction at each point. The job uses logical progress rather than a tradable item,
needs no cutter or personal vehicle, and pays at the final point. Completion is
server-observed. Payout creates one normal wallet entry but no weekly result or
carryover. Allow only the configured active-job count and make accept, progress, expiry,
and completion idempotent. Garrison is rejected at eligibility.

### 7.5 Player commerce

A direct money transfer atomically debits the sender's spendable balance and credits an
identified recipient, producing matched ledger entries and receipts. It creates no
weekly result or carryover. Actor, recipient, value, time, and operation id are visible
to moderation. The ordinary mechanic permits transfers in both directions between
Garrison and regular players, including between a whitelisted identity's own two
characters. Such transfers are additionally surfaced in the Garrison abuse view/security
log; they are not rejected or converted into item provenance.

Items use ordinary world/inventory handoff. Launch has no atomic item-for-money trade,
escrow sale window, squad payroll, or split-on-sale distribution. The server prevents
duplication and forbidden storage, but does not guarantee the fairness of a player
bargain.

### 7.6 Garrison controls

Garrison uses the same safe-zone, Aggressor, death, full-loot, and disconnect rules as
everyone else. Its equipment is unlimited and remains ordinary sellable/lootable gear.
Do not add provenance, an unsellable duplicate catalog, or downstream contamination rules.
Log arsenal withdrawals, Garrison-to-regular money transfers, suspicious repeated
drops/transfers, and direct resale
attempts with stable identity so staff can enforce the whitelist policy through review
and bans.

The Kamensk gear-sale path remains technically available to Garrison so this accepted
trust risk is real and observable. It runs an ordinary gear sale and wallet credit but
never a crystal sale, weekly result, or carryover path. Buying from the regular Kamensk
catalog is rejected.

Garrison is excluded from mining, weekly result, carryover, plot leases, and naming
auctions at the eligibility boundary. Garrison membership never implies cockpit access.

## 8. Mines, Capture, Cutting, and Local Information

### 8.1 Mine aggregate

Each configured mine owns:

- a stable id and authored capture/working bindings;
- stable owner `Neutral`, `Meridian`, or `Granit`;
- optional capture direction and normalized progress;
- a revision;
- configured yield and presentation data;
- owner alarm state and recent cutting-activity samples.

Ownership, active capture direction/progress, and configured yield are public. Capture
state is durable seasonal state and restores across an ordinary restart. It is cleared
only by the full wipe or an explicit audited correction.

### 8.2 Capture calculation

The server samples living, connected Meridian and Granit characters inside the authored
zone. A retained disconnected body is not an active capturer. Locals and Garrison do
not add, subtract, or contest capture progress even when present and fighting.

- a sole corporate numerical advantage moves progress toward that corporation at the
  configured rate;
- equal corporate presence pauses it;
- no corporate presence returns unfinished progress toward the stable owner, or toward
  Neutral when there is no owner;
- reaching the terminal state commits the new owner and resets transient capture data.

There is no population scaling, Activity Index, capture lock, Local owner state, or
passive mine revenue. Presence sampling, progress integration, restart catch-up, and
ownership transition are server-only. Notifications are consequences of the committed
transition.

### 8.3 Cutting action

Every authored face has a stable id. Starting a cycle validates:

- living player and regular-faction eligibility;
- cutter in usable carried inventory;
- corporate ownership permission or unrestricted Local permission;
- face binding and the player's own face cooldown;
- enough capacity for the configured output;
- no incompatible movement/action state.

The accepted action stores its operation id and relevant configuration snapshot. It
occupies the character, prevents normal movement and weapon use, and presents audible
and visible work. Cancellation, interruption, disconnect, incapacitation, death, or
lost permission produces nothing; an in-progress action is not restored after restart.

Completion revalidates the character, cutter, mine permission, face, operation,
inventory graph, and capacity. It then creates the configured quantity once, commits
the player's `(identity, face)` absolute cooldown, records a mine activity sample, and
returns the authoritative completion result. A control change never touches crystal
already created.

Faces have no global depleted/occupied flag. Several players may use one face
concurrently. Only the completing player's cooldown blocks that player from that face.
Failure never silently deletes or drops output.

### 8.4 Local alarm

When a Local completes a cycle at a controlled mine, create or refresh one alarm for
the current owner using an absolute expiry. A neutral mine creates none. The alarm
contains mine id and expiry only. Player identity, squad, exact headcount, carried
amount, and route never enter owner-visible data.

Notifications may be throttled independently of the continuous alarm state. If
ownership changes while the alarm is active, recompute visibility from the committed
owner policy rather than leaking the prior recipient's private state. Persist alarm
expiry so restart neither clears nor lengthens it.

### 8.5 Local activity intelligence

Record only the configured aggregate needed to publish delayed broad activity buckets
per mine. Run publication from server time, with no player identity or exact count in
the Local-visible payload. The Local view never includes live position, route,
inventory, vehicle cargo, or faction of cutters. Joining late receives only the current
eligible delayed snapshot.

This information path is distinct from the owner alarm. Neither changes yield, price,
permission, capture, or leaderboard credit.

## 9. Kolguyevite Inventory Model

Kolguyevite is one quantity-bearing resource/item type with weight and capacity scaling
by amount. It has no origin, faction, mine, extractor, holder, week, purity, grade, or
price band. The representation must merge/split quantities without spawning one
replicated entity per abstract unit.

Allowed locations are character/backpack inventory, vehicle cargo, corpse, temporary
public loot container, and ordinary open world. It is legal in a registered vehicle
inside a protected city and on a legitimately saved character.

It is forbidden anywhere in the secure-storage item tree. The server checks:

- direct item insertion;
- resource insertion and quantity merge;
- item replacement;
- a container with nested crystal moving into secure storage;
- crystal moving into a container whose ancestor is secure storage;
- bulk transfer and quick-move routes;
- saved-loadout, arsenal refund/sell, dismantle, and other conversion paths.

Both the incoming subtree and destination ancestor chain are inspected. A disabled
client action is feedback only. The dedicated NPC crystal-sale operation is the only
path that converts kolguyevite directly into money, result, and carryover.

## 10. One Secure-Storage Pool and Overflow

### 10.1 Logical model

Each regular player has exactly one server-owned secure-storage aggregate. The home
locker and each active leased plot whose Storage Expansion is installed are
authenticated views into that same item graph. A plot shell or lease without the module
does not expose storage. Terminals are not separate physical inventories, synchronized
copies, or a transfer route.

Consequently, eligible gear deposited through a Kamensk plot terminal is immediately
available at the Ugoldar home terminal and vice versa. This cross-city access is an
accepted plot benefit. Kolguyevite remains forbidden and therefore cannot use it to
bypass hauling.

Only the owner may open or mutate the pool. Opening a terminal validates its authored
identity, faction/service access, active plot lease and installed Storage Expansion
where applicable, distance/use state, and absence of Aggressor status. Mutations
revalidate those conditions, item eligibility, expected storage revision, and capacity
on the server.

Use one canonical serialized item graph. If the engine requires temporary entity
materialization for inventory UI, only one authoritative terminal session may own a
given mutable revision at a time, or concurrent sessions must use revision-conflict
rejection. Never materialize two independently writable copies.

### 10.2 Capacity

Effective capacity is the configured base entitlement plus the additive configured
bonus of every Storage Expansion installed on one of that player's active plots. Each
plot has only one module socket and can contribute at most once; bonuses from several
plots stack in the same pool. Capacity is a logical policy over that one pool. The
physical serializer/backing storage must tolerate the maximum supported contents and
subsequent overflow; it must not destroy items merely because the entitlement decreases.

The owner UI reports base entitlement, each active bonus, effective capacity, used
capacity, free capacity, and overflow amount from the authoritative calculation.

### 10.3 Overflow behaviour

Lease/module loss or a configuration decrease applies the new capacity immediately
without moving, dropping, or deleting contents. When used capacity is above entitlement:

- every existing item remains visible and withdrawable;
- every inbound store, resource-store, merge, or replacement path from outside the
  aggregate is rejected at every terminal, even when it would not increase total use;
- withdrawals and purely internal rearrangement within the existing item graph are
  allowed;
- ordinary deposits resume automatically once use is within capacity.

There is no separate overflow inventory. “Overflow” is the state `used > entitlement`
on the same item graph. Regaining an active Storage Expansion bonus can clear it without
an item transfer. Faction change and full wipe deliberately clear the whole pool through
their explicit destructive workflows; ordinary death does not.

## 11. Registered Vehicles

### 11.1 Scope and records

Only a purchase through an eligible configured garage catalog creates a registration.
Whitelist by exact configured vehicle definition, or an explicitly configured prefab
ancestry rule. An ambient vehicle that looks similar never becomes registered.

`VehicleRegistration` contains at least:

- registration id, current Vakhta id, owner backend identity, and vehicle definition;
- state `Garage`, `World`, or `Lost`;
- one owner-managed ACL of backend identities;
- optional current deployment id;
- revision and last transition operation;
- last loss reason and restoration status needed for receipts.

A player may own several registrations. The effective configured deployed limit counts
that owner's registrations in functional `World` state. Each registration has at most
one functional instance. A lowered cap grandfathers existing functional deployments;
while the count is at or above the cap, a deploy command cannot increase it.

`VehicleDeployment` binds a registration to one persistent world entity and records
whether destruction/cleanup and cargo finalization have occurred. An inert wreck is
not functional even if its entity remains for the engine garbage collector.

### 11.2 Purchase and deployment

Purchase debits money and creates the registration exactly once for the current Vakhta.
Deployment itself is free but remains a checkpoint-gated registered-property
transition. Adapt Conflict's catalog-spawner preview pattern: inside the garage's
authored deployment area, show the selected registered vehicle as a local green/red
`SCR_PrefabPreviewEntity` with the proposed transform. The preview is guidance only and
never grants authority.

On confirmation:

1. validate the audited owner, `Garage` state, exact whitelisted vehicle definition,
   deployed count, garage access, Aggressor state, and candidate transform inside the
   authored deployment area;
2. resolve the definition's authoritative footprint and recheck terrain/slope, world
   overlap, overhead/side clearance, and a configured usable exit corridor on the
   server; do not trust the client's preview color or bounds;
3. reserve the registration/deployed slot only after those checks, spawn one
   authoritative entity at the accepted transform, and attach a fresh deployment id;
4. persist the entity binding and `World` state; and
5. publish the owner marker and receipt.

If the final spatial check fails, spawning fails, or another entity wins the race, make
no deployment-state change, charge nothing, create no functional instance, and return
the precise obstruction/refusal result. The owner chooses another valid transform or
waits for the obstruction to move. There is no garage towing, forced displacement,
automatic return, or operator "clear exit" shortcut.

A retry or reconnect resumes this operation; it cannot spawn a second instance. If the
registered functional vehicle remains anywhere in the world, the garage refuses a new
one. The owner uses the private marker to travel back, gets help, or waits for ordinary
abandonment cleanup; death elsewhere is not replacement eligibility.

The marker payload is replicated only to the owner and authorized cockpit observers.
Do not broadcast all registered positions and hide icons on clients.

### 11.3 Access list

The owner is always authorized and may add or remove named players through a
server-validated, revisioned ACL command. Faction membership alone grants nothing. The
same list covers all seats and cargo access; there is no PIN, shared code, per-seat
matrix, or separate cargo list. It persists through return, destruction, and
restoration during the Vakhta.

Client action hooks provide immediate refusal text for entering and changing seats,
but are not security. The server audits compartment changes and removes/rejects an
unauthorized occupant. Every get-in, switch-seat, turret, and compartment path must be
covered. Cargo inventory removal and quick-transfer use server-authoritative inventory
vetoes. Attempts are security events.

Outside protected cities, unauthorized players may damage and destroy the vehicle.
The ACL does not create damage immunity. The sole bypass is removal of any corpse from
a compartment; it grants no seat possession or cargo rights. Vanilla's casualty action
may reject extraction from an active hostile vehicle, so enumerate and override that
gate explicitly rather than treating the stock action as proof of this exception.

An ACL-authorized player may return the physical vehicle. Only the owner may deploy a
registration, pay to restore it, or change its ACL. `ReturnVehicle` is checked as a
narrow exception before the correct owner garage's ordinary faction-service gate, so a
cross-faction ACL member can return the machine without gaining any other garage action.

### 11.4 Return and repair

`World -> Garage` is allowed only through the registration's correct owner-garage
terminal while the bound live vehicle is physically present, fully repaired by the
ordinary repair system, empty, unoccupied, and the actor is the owner or on its ACL. The
transition despawns/stores that functional instance once and clears the owner marker. It
never teleports cargo, repairs for free, or recalls a remote vehicle.

### 11.5 Destruction, cargo, and restoration

On authoritative destruction:

1. claim a unique destruction-finalization operation;
2. mark the deployment non-functional and registration `Lost`;
3. move each remaining top-level cargo entity exactly once to one temporary public
   crate at the wreck; nested contents remain inside their top-level containers;
4. persist the crate binding and finalized item set;
5. publish loss and restoration information.

Callbacks, restarts, streaming, and cockpit retry must converge on the same operation
and crate. They may not duplicate or silently destroy cargo. If crate creation fails,
hold the aggregate for recovery rather than minting a new untracked set.

After the configured restoration payment, `Lost -> Garage` makes the registration
deployable again. A wreck may still exist until normal garbage collection; correctness
depends on the logical functional state, not immediate wreck deletion. Do not delete an
old wreck merely to permit restoration or deployment; the engine garbage collector owns
its eventual removal.

### 11.6 Abandonment and garbage collection

Use the engine's normal proximity/relevance-sensitive abandonment policy and timing;
registered vehicles get no separate absolute or in-city lifetime. Immediately before
garbage collection deletes a live registered vehicle, commit `World -> Lost` for that
exact deployment. Cargo removed with an abandoned live vehicle is not returned to the
owner, storage, garage, or a public crate. The owner is told the loss reason and
restoration price.

If the pre-delete hook must defer deletion until cargo finalization
completes, explicitly reinsert/retrack the entity with `GarbageSystem` after declining
that deletion attempt. The native pre-delete path stops tracking even when a listener
vetoes removal; assuming it will retry by itself creates a permanent deployed-slot
ghost. Once finalization is durable, permit the normal GC attempt to remove the entity.

Distinguish confirmed abandonment deletion from temporary streaming, persistence load,
planned shutdown, and inert-wreck cleanup. Startup reconciliation must not mark a valid
persisted vehicle Lost merely because its entity has not finished loading. Conversely,
a logically `World` registration with a confirmed missing functional entity cannot
remain a permanent deployed-slot ghost; it enters a recoverable incident and then the
audited loss path.

Because normal GC depends on nearby players, a registered vehicle and its legal cargo
may remain world-relevant for a long time in a busy protected city. This accepted,
bounded storage consequence still consumes one configured deployed slot and ends on
ordinary cleanup, destruction, return, or wipe; do not add a second proximity-
independent expiry system to counter it.

There is no remote recall, vehicle sale, retirement refund, insurance, theft code, PIN,
or public/shareable/additional tracking beacon beyond the private owner marker. Full
wipe removes all registrations, ACLs, deployments, physical registered vehicles, their
cargo, restoration state, and garage state.

## 12. Plots, Fixed Buildings, and Lease Effects

### 12.1 Authored plots and shells

Each enabled plot has a stable id, city, optional Ugoldar faction, authored plot region,
one permanent building shell/interior, one management-console binding, one visual module
socket, current lease, future lease slot, and optional installed-module record. The
shell is map infrastructure: it is present before bidding, remains the same for every
holder, is publicly traversable, and survives ordinary restart, lease transitions, and
the full wipe. It is not player property and is not spawned or reconstructed from
`PlotState`. Author it as non-destructible/non-editable service infrastructure and
validate its footprint against roads, neighbouring terminals, protected-city exits and
garage deployment space. A bad shell placement is corrected in the map/configuration,
not through a player construction-removal command.

Ugoldar eligibility requires the matching regular faction. Kamensk accepts any regular
faction and may enforce the configured per-faction limit. The configured personal lease
limit spans both cities. Garrison is ineligible. If a limit is reduced below active or
already-settled future holdings, preserve those awards through their current terms. New
bid admission calculates projected post-transition holdings under the new limit; an
over-limit grant cannot be renewed or expanded.

The shell and its empty socket grant no spawn, inventory, storage capacity, passive
income, or private interior. An active lease grants management authority at the console
and eligibility to buy the one launch module. The socket is only an authored visual/
binding point; it is never a second interaction authority or physical container. Plot
actions—not access to the building—are owner-gated.

### 12.2 Storage Expansion

Launch has exactly one plot module definition: **Storage Expansion**. It has no tiers.
A plot has one fixed socket and therefore at most one installation. Do not build a
generic construction catalog, free-placement editor, construction-material economy, or
speculative multi-module framework. Any later module needs its own game-design and
technical decision before it enters this contract.

The leaseholder buys the expansion directly at the authored console. It is an
idempotent personal-money command, not an inventory item, kit, blueprint, world pickup,
or tradeable object. Validate audited owner, active lease/revision/expiry, empty socket,
the single configured definition and price revision, spendable balance, Aggressor state,
distance/use state, and operation id. Commit the debit and an installation record with
plot id, leaseholder, definition, exact paid amount, configuration revision and time.
If an authored cosmetic socket state is shown, derive it from that record; the visual
entity does not own entitlement.

An installed expansion changes that same console from management/purchase-only to also
being an authenticated terminal into the holder's one secure-storage item graph. It
adds the configured capacity bonus while that lease is active. It creates no separate
plot inventory: gear placed through it is immediately available from the home locker
and every other active expanded plot terminal. Each plot contributes once, and bonuses
from several active plots stack additively.

### 12.3 Lease transition

Auction payment is the full lease price. There is no recurring rent.

At a term boundary, after applying any incident extension from section 13.6:

- if the same player won the next term, update the lease and retain the installed
  Storage Expansion, exact paid-cost record, terminal access, and bonus;
- if a different player won, or no valid renewal and no incident extension exists,
  revoke management/storage actions, remove the old installation and capacity bonus
  exactly once, and credit the configured compensation percentage of that module's
  exact recorded personal-money payment;
- never create or return a module item, kit, or blueprint;
- let the shared pool enter withdrawal-only overflow when capacity falls; and
- activate the selected future lease only after prior module removal/compensation is
  committed.

Use one idempotent transition operation per plot and term. A destructive regular-
faction change removes the player's leases and modules without lease refund or module
compensation. A lease never crosses a full wipe: wipe removes lease/module state and
provides no compensation, while the permanent authored empty shell/console/socket remain
part of the map.

## 13. Unified Auction and Naming System

### 13.1 Core lot state machine

Plot leases and next-Vakhta naming rights use the same sealed first-price auction core
with narrow reward adapters.

Lot states are:

`Draft -> Scheduled -> Open <-> Paused -> Locked -> Settled`

`Cancelled` is a terminal path from `Draft`, `Scheduled`, `Open`, or `Paused` through an
authorized refund operation. `Locked` has no cancellation edge: its recorded
deterministic settlement must finish or use an explicit compensating repair. Every
transition validates the expected revision, permissions, schedule, and adapter.
`Locked` accepts no bid mutation and freezes the candidate set for idempotent
settlement.

Each lot stores its reward adapter, eligibility and terms snapshot, published open and
close times, current state, revision, settlement operation, and result. Normal closure
uses the published fixed time. A cockpit pause/extension after an incident is a visible,
audited schedule change, not an automatic soft close.

### 13.2 Bids and escrow

A player has at most one current exact bid per lot. While `Open`, the eligible bidder
may create, replace, or withdraw it. The server:

1. locks the wallet and lot/bid aggregate;
2. validates eligibility, lot revision, amount, spendable funds, and adapter capacity;
3. reserves the exact new amount and releases the old amount atomically;
4. assigns a new monotonically increasing accepted sequence to every accepted creation
   or revision;
5. persists the bid and receipt before replying.

Withdrawal releases the reservation and closes that bid revision. Reserved funds
cannot be spent, transferred, or reserved elsewhere. A retry returns the same accepted
bid instead of taking another sequence or reservation.

Before lock, only the bidder sees their own amount/status and wallet reservation.
Competing bids, bidder identities, bid values, bid count, and current leader are not
available to any other player or cockpit role. Operators may see lot state, deadline,
and health/invariant failures without seeing sealed contents. Post-lock settlement
records follow the appropriate cockpit permission and audit policy.

### 13.3 Settlement and refunds

Settlement orders valid current bids by:

1. greatest exact amount;
2. earliest accepted sequence for equal amounts.

A revision receives a new sequence. The highest valid bidder wins and pays the full
submitted amount. Revalidate adapter eligibility at settlement; an invalid candidate is
refunded and the deterministic ordering continues to the next valid candidate. Losing,
withdrawn, invalid, and cancelled bids release their full reservations.

Settlement uses one checkpoint-gated operation that records the frozen bid revisions,
winner, payment ledger entry, adapter result, all releases, and receipt set. Restart or
manual retry completes missing effects without charging, refunding, assigning a lease,
or applying a name twice. A lot cannot become `Settled` until every reservation is
accounted for.

There is no minimum-increment contest, proxy maximum, soft-close rule, incumbent bonus,
escalating occupancy premium, or operator-picked normal winner.

### 13.4 Plot adapter

An accepted plot bid reserves one future personal lease slot. Capacity checks include
current leases, expiring leases, renewals, and current future-slot reservations so no
newly accepted set of simultaneous wins can make projected post-transition holdings
exceed the configured personal or Kamensk faction limit. Grandfathered active or
already-settled rights survive a later cap decrease but do not create room for renewal
or expansion above the new cap. A lease approaching expiry may support a renewal bid
for that plot or use the released future capacity elsewhere, but never reserve the same
slot several times.

Lots sharing a close time settle in a published stable order, using their configured
priority and stable lot id rather than callback timing. At each lot, revalidate the
ranked candidates against capacity already assigned by earlier lots. If the leading
candidate is now ineligible, refund that bid and continue through the same sealed order
until a valid winner is found or the lot receives no leaseholder.

Settlement writes the plot's future lease and retains the winning payment as the entire
lease price. The lease transition in section 12 applies it at the configured boundary.

### 13.5 Naming adapter

Only configured map-label targets are auctionable. A player submits a candidate through
moderation before bidding. Approval binds the exact normalized/display name to that
player, target, and lot. A naming bid must reference that approved candidate; the
candidate cannot change while the bid is active or after the lot locks.

Settlement creates one `NamingAssignment` for the next Vakhta. The wipe bridge applies
it exactly once; no valid winner leaves the canonical name. An assignment expires with
that next Vakhta and grants no gameplay power, permanent title, monument, or separate
currency.

### 13.6 Incident controls

Through audited domain commands, authorized operators may schedule, pause, resume with
a published close, extend, cancel/refund a pre-lock lot, retry failed settlement, or
correct a proven system fault. They cannot edit or fabricate a player's bid, change its
accepted sequence, expose sealed data publicly, or select a different normal winner.

The plot adapter protects an incumbent from an incident cancellation: cancel/refund
requires a replacement lot with a published close, and the current lease continues
without additional rent until that replacement closes and settles. An already-unleased
plot remains unleased. Cancelling a naming lot produces no assignment, so its canonical
map label remains.

After an outage, first determine from durable accepted timestamps whether the server
accepted bids continuously through the published close. If it did, lock and settle the
lot normally. If it did not, operators must publish an extension or cancel/refund while
the bids remain sealed. Once any competing bid or provisional outcome has been
unsealed, operators may only finish or repair the deterministic recorded result; they
cannot extend, cancel, or choose a policy after seeing which outcome it produces.

## 14. Weekly Results, Carryover, Rollover, and Faction Changes

### 14.1 Sale-derived results

`CrystalSale` is the sole scoring event. It stores seller identity, seller faction at
commit, week id, accepted quantity, proceeds, and carryover contribution. Personal
weekly totals and the current faction widget derive from these committed rows.

Personal ranking uses quantity sold. Equal totals share rank; do not introduce an
unpublished combat, revenue, time, or identity tiebreaker. Locals use the same ranking
rules. Garrison is excluded. The faction widget is only the current-week sum by
faction-at-sale and creates no winner or reward.

Keep completed week snapshots available until wipe and optionally export them before
deletion. The launch game does not require a permanent in-game leaderboard archive.

### 14.2 Carryover

For each crystal sale, calculate the configured share of money proceeds and credit no
more than that player's remaining configured cap for that week. Store both the uncapped
calculation inputs and committed contribution on the sale/weekly record so a retry or
later configuration change cannot alter it.

Gear sales, jobs, transfers, refunds, plot compensation, admin compensation, purchases,
and every non-crystal-sale ledger reason are structurally unable to invoke carryover.
Unused cap does not move between weeks. Crystal held across a boundary counts only when
the sale commits.

The wipe reads the current `CarryoverWeek` aggregates, not historical receipt fields on
sale rows. A faction change appends an audited forfeiture/clear operation and zeroes the
eligible aggregates; preserving those sale rows for the leaderboard must never recreate
their forfeited carryover.

### 14.3 Week rollover

The calendar service creates deterministic week ids and runs one idempotent rollover
operation:

1. stop assigning new commits to the closing id at the authoritative boundary;
2. finalize its immutable leaderboard snapshot and carryover record;
3. open the next configured week/cap;
4. publish the new current state and retain the completed view.

Sales concurrent with the boundary serialize against this operation. Restart catch-up
can perform it again safely.

### 14.4 Regular-faction change

Faction change is a destructive, previewed player command that applies to the regular
character only; a whitelisted identity's Garrison character is untouched by it.
Implement it as a resumable checkpointed job with no window in which assets from both
factions coexist:

1. validate that the actor is alive, on foot, unmarked, in interaction range of the
   authored Ugoldar faction-administration service, and eligible for the target faction;
2. preflight every owned deployment and refuse while any registered vehicle contains a
   living or dead occupant; also refuse while any owned bid is `Locked` or settling;
3. close the player and their registrations to new value, seat, cargo, bid, and plot
   mutations;
4. recheck occupancy and bid states, then cancel every `Open` or `Paused` bid and
   release its matching reservation;
5. relinquish current and already-settled future plot rights, remove their installed
   Storage Expansions and capacity bonuses, and issue no lease refund or module
   compensation;
6. remove unoccupied registered vehicles and their cargo without recovery, then remove
   registrations, ACLs, garage/restoration state, carried equipment, and the complete
   secure-storage/overflow pool;
7. clear wallet balance and every current carryover aggregate;
8. assign the new faction and fresh character, then reopen mutations.

Preserve every committed sale row, including the still-open week's rows, with its
original faction-at-sale. The personal board continues to count those sales and the
faction widget keeps them under the faction that received them at commit. Also preserve
the Vakhta's starter-loadout-issued and starter-cutter-issued flags so switching cannot
duplicate either grant. Current carryover is nevertheless cleared; the two are
separate records and consequences. Preserve a `NamingAssignment` created by an already-
settled lot: it is a completed personal purchase, not a current faction entitlement.

## 15. Player UI, Replication, and Receipts

### 15.1 Visibility classes

Classify each payload before implementing replication:

| Visibility | Examples |
|---|---|
| public | Vakhta/week dates, personal leaderboard, faction statistic, mine owner/capture/yield, zone and service markers |
| current player | money/reserved balance, carryover cap, Aggressor expiry, face cooldowns, storage/overflow, own bids, receipts |

Never send a secret to every client and depend on client UI to hide it.

### 15.2 Replication pattern

Large maps of wallets, bids, storage items, vehicles, weekly rows, or audit entries are
not replicated as one continuously changing property. Use:

- small public summaries;
- scoped snapshots requested after authentication;
- revisioned deltas after committed mutations;
- pagination for histories and cockpit tables;
- join-in-progress snapshots followed by deltas;
- absolute server timestamps so clients render countdowns locally without owning them.

A missed revision triggers a fresh scoped snapshot. UI optimistic state is discarded on
server refusal. World markers are similarly scoped and removed when entitlement ends.

### 15.3 Required feedback

At the point of use, display the live effective values and reasoned state listed in
`RULES.md`: calendar and rankings; faction counts, admission limits, transient invites,
eligibility/change consequences; zone and Aggressor state; mine control, yield, action
and cooldown; Local intelligence/alarms; market quote and carryover effect; storage
capacity/overflow; plot lease/module/auction terms and own reservation; vehicle state,
limit, ACL, placement validity, location, cleanup, and restoration.

Every consequential server transaction—money, NPC item conversion, registered
property, auction/lease settlement, or operator compensation—creates a receipt keyed by
operation id. Routine movement and low-level inventory actions need clear feedback and
audit where security-sensitive, but do not create a permanent receipt each time.
Offline consequential results queue for the owner and remain queryable under the
configured retention. Rejections use stable localized reason codes plus the current
authoritative value needed to correct the request.

## 16. Operator Cockpit, Audit, Telemetry, and Backups

### 16.1 Cockpit boundary

The cockpit is launch-critical because early Vakhtas will be operated manually. The
launch cockpit is an in-game admin panel: an owner-side PlayerController component sends
reliable requests to the authoritative server, and the server returns only role-scoped,
paginated snapshots, deltas, and results to that owner. It calls the same domain
services as gameplay and is never direct persistence access. It must not expose raw
record/file editing, arbitrary script execution, unrestricted entity deletion, or
unvalidated field editing.

Use separate least-privilege roles, for example read-only observer, moderator,
operator, and owner. Garrison membership is unrelated. Sensitive actions require fresh
authorization, an entered reason, expected revision, preview, and explicit confirmation.
Global destructive actions additionally require a verified backup.

Resolve staff permissions from the server-audited stable player UUID. Prefer the
engine's UUID-based role API after proving it on the production dedicated server; if
that platform feature is unavailable, use an operator-owned UUID-to-role configuration
and keep temporary assignments in the local backend. A transient connection id,
display name, faction, or client claim is never authority.

### 16.2 Required views and commands

Launch coverage includes:

- server health, local backend readiness and contract version, answer times and
  refusal counts, physical-world save state and duration, replication health, and
  configuration revision;
- players, audited UUID readiness, projected faction counts/limits, invitation state,
  faction/whitelist state, online/dead/retained character state, Aggressor expiry,
  Garrison-boundary grace, moderation notes, and bans;
- wallet ledger, transactions, sales, carryover, weekly totals, transfers, recovery
  jobs, and Garrison arsenal activity;
- mine owner/capture, face/cooldown diagnostics, alarms, activity publication, and zone
  binding health;
- secure-storage use/overflow, terminal sessions, and crystal-violation attempts;
- vehicle registrations, deployments, ACLs, markers, destruction/cargo finalization,
  GC status, loss and restoration;
- plots, authored binding health, leases, installed Storage Expansions, future slots,
  module removal/compensation, auction lots, aggregate reservation health without live
  sealed contents, post-lock
  settlement/refund, candidate approval, and naming assignments;
- week rollover, Vakhta lifecycle, wipe preview/progress/retry, exports, backups,
  incidents, and broadcasts.

This is the required launch cockpit, not an optional post-launch dashboard. To keep its
size from blocking the first technical playtest as one undifferentiated deliverable,
ship an initial vertical slice before that playtest: UUID/RBAC and audit; health,
configuration revision, checkpoint queue/backpressure, maintenance, manual checkpoint
and broadcast; player/faction/whitelist/ban and retained-body/Aggressor views; wallet/
ledger lookup with explicit compensation; mine/capture/alarm state; and vehicle
registration/loss/reconciliation incidents. Before plots or auctions are enabled in a
playtest, add their full views and invariant-preserving pause/refund/retry controls.
Every remaining view above is still mandatory before launch. A subsystem may not open
to players merely because its cockpit panel was deferred.

Corrections call explicit compensating domain commands. Examples are crediting a proven
missing payout, retrying a stuck cargo finalization or settlement, marking a confirmed
missing deployment Lost, or repairing a binding after evidence review. A correction
cannot silently rewrite a completed sale/transfer, delete overflow items, clear a
legitimate Aggressor consequence, edit a bid, choose a normal auction winner, create a
duplicate registered vehicle, or remove a retained body to protect its inventory.

### 16.3 Remote bridge and host supervisor

Remote control at launch is deliberately narrower than the in-game cockpit. Register
one custom RCON command namespace whose allowlisted commands call the same validated
domain service. Limit it to health/status, maintenance on/off, checkpoint request,
graceful stop/restart request, broadcast, and specifically implemented compensating
operations. Do not expose arbitrary command evaluation or raw state editing. The exact
RCON authentication, permissions, response limits, and reconnect behaviour must be
proven on the production dedicated-server setup.

An external service manager—not Enforce Script—owns process start, crash restart,
executable/addon/config deployment, RCON secrets, log shipping, and cold backup/restore.
Engine transitions may request a graceful restart or termination but cannot relaunch a
crashed process. Obsolete `DSSession` restart/shutdown calls are not an implementation
path.

A later website synchronises with the local backend, never with the game, and is
read-only with respect to the game. It is outside the launch authority path; anything
it changes goes through the same validated domain commands.

### 16.4 Audit and security events

Append an application-append-only audit entry for every cockpit command and high-value
mutation. Store actor, role, reason, command/operation id, target, request, expected and
actual revision, before/after references or hashes, time, outcome, and correlation id.
Corrections append; they do not alter the original entry. The audit trail lives in the
local backend and is shipped to off-host retention by the host log/audit shipper so an
in-process operator cannot silently rewrite the only copy.

High-value security events include duplicate operation ids with changed payloads,
garage spawn races, impossible wallet/reservation states, Garrison equipment or money
feeding,
attempted sealed-bid access, configuration changes, backup/restore, and wipe lifecycle
actions. Repeated forbidden storage and unauthorized vehicle attempts are rate-limited,
aggregated by actor/reason/target, and sampled; a hostile client cannot force an
unbounded durable-write stream.

Operational telemetry should expose rates and stuck-state ages without becoming game
authority: failed physical-world saves, backend refusals and timeouts, incomplete physical stages
of accepted operations, reconcile incidents, retained bodies, transaction rejection reasons, cargo-
finalization failures, unreleased auction reservations, overdue rollovers, and backup
age.

### 16.5 Backups and restore

Create versioned backups on the configured schedule and before every global destructive
workflow. The safe launch procedure is: enter maintenance, reject new mutations,
request a blocking native checkpoint, wait for its successful save id, terminate the
server gracefully so files are closed, and let the host supervisor snapshot the complete
resolved persistence/profile roots together with server configuration, addon/build
versions, schema/config revisions, and a hash manifest. Ship the matched snapshot
off-host, then restart through the proven resume path. Do not hot-copy active
persistence files; the local engine API does not prove that safe.

Restore is offline: stop the process, archive the current complete roots, restore one
matched snapshot, start a staging instance, run migrations/reconciliation/invariant
checks, and explicitly promote it. Never restore only the logical state or replace files
under connected players. Record the restore and source backup in the retained
operational audit.

## 17. Vakhta Wipe

A full wipe is a purpose-built, resumable maintenance job. Do not implement it by
calling the generic game-mode end path: engine game-end handling can disable saving and
purge session persistence.

The wipe workflow is:

1. enter maintenance and stop new joins and gameplay mutations;
2. finish or explicitly recover pending consequential commands and incomplete
   lifecycle stages;
3. lock due auctions and resolve every reservation according to the published policy;
4. create a blocking checkpoint, request graceful termination, let the host supervisor
   snapshot and verify the closed persistence/profile roots, then resume this same job
   in maintenance from that checkpoint; optionally export completed weekly
   leaderboards/audit summaries;
5. calculate each eligible carryover amount from committed capped weekly aggregates
   exactly once, combine it with the configured next-Vakhta opening balance, and stage
   valid next-Vakhta naming assignments;
6. create the new Vakhta id/config snapshot;
7. clear old balances after calculation, current regular-faction registrations, player
   carried/world items, characters, Aggressor state, secure storage and overflow, mine owner/capture/
   cooldowns/alarms/activity, plot leases and installed Storage Expansions (but not the
   authored shells/consoles/sockets), bids/reservations, weekly boards, registered
   vehicles/cargo, registrations, ACLs, garage/restoration state, starter loadout/cutter
   flags, and all other Vakhta gameplay state;
8. apply staged opening balances and map names exactly once to the new Vakhta;
9. validate zero stale reservations/deployments/leases and all global invariants;
10. checkpoint the completed job, publish the new calendar, and reopen the server.

Each stage stores a checkpoint and is safe to resume. A crash cannot apply opening money
or a naming assignment twice, nor expose a half-old/half-new world. Naming assignments
survive only this bridge and expire with the new Vakhta. Account authentication,
cockpit role assignments, bans/moderation records, operational audit, backup catalog,
and configuration history are not gameplay rewards and remain under their retention
policy.

There is no requirement for a large permanent in-game leaderboard archive. A simple
pre-wipe export is sufficient if configured; otherwise the old live boards are cleared.

## 19. Required Technical Spikes

Resolve these with isolated prototypes before building dependent content:

1. **Quantity-bearing crystal:** prove merge/split, weight/capacity scaling,
   persistence, death, world drop, and vehicle cargo without one entity per unit.
2. **Recursive secure veto:** prove every direct, nested, replace, resource, bulk,
   loadout, refund, sale, and conversion route rejects crystal while normal corpse and
   vehicle handling still work.
3. **Shared remote storage and owner-only streaming:** prove one native persistent item
   graph, with no inventory owned by the home or plot console, can be used safely from
   the home locker and every active expanded-plot console, including the farthest
   authored cross-city pair. Cover cross-city withdrawal, simultaneous attempts,
   revision conflict, restart, nested containers, capacity loss and withdrawal-only
   overflow. With two or more owners using adjacent terminals, prove that only the
   authenticated owner receives that pool's item identities, contents and deltas; a
   stock client must not discover another pool through vicinity replication.
4. **Backend call durability and performance:** prove NPC sale/purchase, recovery
   completion/payout, money transfer, bid reservation/settlement, Storage Expansion
   purchase/removal compensation, registered-vehicle transitions/cargo finalization,
   faction change, operator compensation and wipe never acknowledge a result the local
   backend has not recorded and never duplicate money or property. Force game-process
   loss before the call, while the answer is pending, and after acceptance but before
   the physical effect; force backend loss at the same points. At target player/item/
   vehicle/storage counts, measure answer time and sustainable command rate over the
   loopback interface, then set the launch answer-time limit and re-check interval from
   those measurements. For routine extraction and secure storage, prove revision
   safety, consistent physical checkpoints, no duplicate item graph, and the documented
   bounded rollback instead of a backend call per move.
5. **Aggressor attribution:** cover firearm, vehicle weapon, grenade, release/trigger/
   remote detonation of an offensive explosive, detonator-action controller position,
   delayed damage, damage to any other player regardless of faction, and damage to
   another player's occupied or registered vehicle. For collision, prove contact-time
   pilot identity plus accepted positive damage at the configured threshold; prove
   ambiguous callback/current-seat cases mark nobody.
6. **Safe-zone enforcement:** prove rejection when either the protected target or the
   authoritative attack source/fire origin is inside, including an outward projectile
   and an outside explosive triggered by a controller inside. Prove player-driven impact
   veto even when driver attribution is unavailable. Also prove immediate Aggressor
   death across fast boundary crossing, vehicle entry, spawn, reconnect and event-order
   races, while the vehicle itself continues ordinary physics/ACL/cargo behavior.
7. **Disconnect and offline-character persistence:** prove Quit, network timeout,
   client crash and kick all use the same retained body; prove the configured five-
   minute launch base, later-of-Aggressor deadline, retained vehicle seat, same-entity
   reconnect, live-expiry save/remove, later saved-position reconnect, death race and
   planned shutdown. Restart with several offline saved characters, wait beyond the
   vanilla cleanup timeout, and prove `SelfSpawn = false`, `SelfDelete = false` plus the
   replacement serializer preserve exactly one character for each later audited owner.
8. **Vehicle placement and authority:** prove the Conflict-style local preview and
   server-side deployment-area, full-footprint, terrain/overlap/clearance recheck; an
   obstruction race must leave the registration in `Garage`, charge nothing and create
   no instance. Enumerate every native get-in/change-compartment/cargo-removal path and
   prove server rejection/ejection without client cooperation. Override the stock
   casualty gate so every dead occupant remains extractable. Prove a cross-faction ACL
   member can invoke only `ReturnVehicle` at the correct owner garage, while deploy,
   restoration, ACL editing and all other faction-gated actions stay denied.
9. **Vehicle persistence and GC:** distinguish load/streaming from confirmed
   abandonment, reconcile restart, finalize destruction cargo once, allow restoration
   while an inert wreck remains, and prove a deployed-cap decrease grandfathers existing
   vehicles while refusing every count-increasing deployment at or above the new cap.
   Prove a pre-delete veto followed by explicit re-insertion is retried, nearby players
   may legitimately extend lifetime, and an inert wreck need not be deleted before
   restoration/deployment.
10. **Fixed plot module binding:** prove every enabled plot binds exactly one permanent
    authored shell, console and visual socket, that the empty shell owns no storage or
    inventory, that the console can switch between management-only and storage-terminal
    behaviour from `PlotState` without a physical module entity, and that no
    free-placement, build, or dismantle path reaches the shell or socket. Purchase,
    compensation, stacking, renewal, and cap-decrease behaviour are domain tests in
    section 20.1, not engine questions.
11. **Native persistence and unattended resume:** register the physical-world records
    (retained characters, storage roots and items, vehicles, structures) in one
    `WorldState`, force a kill during save, and prove restart selects either the prior or new complete valid
    save. Prove the exact dedicated-server save selection, compatibility/migration,
    and fail-closed behaviour; do not invent an unverified command-line flag.
12. **In-game cockpit:** prove post-audit stable-UUID RBAC, owner RPC requests, scoped pagination,
    revision checks, confirmation, and domain invariants. Verify the engine role API or
    exercise the configured UUID-role fallback, and prove no cockpit role receives live
    sealed-bid contents.
13. **RCON adapter:** prove the custom allowlisted command namespace, authentication,
    permissions, response limits, timeouts and calls into the same domain commands.
14. **Lifecycle and supervisor:** prove maintenance gating, blocking shutdown
    checkpoint, graceful transition request, external crash detection/restart and exact
    unattended save resume. Do not depend on obsolete `DSSession` process control.
15. **Cold backup and restore:** prove closed-file snapshot, manifest verification,
    off-host copy, matched configuration/addon versions, staging migration/reconcile and
    explicit promotion of a complete restore.

Auction ordering/crash recovery, faction-change consequences and recovery-job admission
remain mandatory automated domain tests in section 20.1; they are not separate engine
spikes.

A failed spike changes the implementation approach, not the player rule without a new
design decision.

## 21. Explicit Launch Exclusions and Accepted Consequences

Do not implement these superseded systems:

- Activity Index or population-scaled economy/capture;
- faction victory, shipment boat, season banner, finale multiplier, or faction reward;
- crystal provenance, origin week, mine grade, purity, holder, or fresh-crystal surge;
- Local yield penalty, extraction quota/ledger, Local mine ownership, or corporate
  extraction from neutral/enemy mines;
- mine buyback, alarm price suppression, defence contract, passive mine income, or
  faction treasury;
- atomic player trade, item-for-money escrow window, split-on-sale, or squad payroll;
- dynamic pricing, story contracts, broad quest system, and world events beyond narrow
  recovery jobs;
- Garrison event schedule, combat immunity, progression, or item provenance economy;
- vehicle PIN/code, public/shareable/additional tracker beyond the private owner marker,
  registered-vehicle theft, insurance, sale, retirement refund, remote recall, garage
  towing, or a custom proximity-independent cleanup timer;
- free plot construction/placement, physical build kits, module tiers, a speculative
  multi-module framework, plot spawn, destructible plot raids, separate plot storage,
  additional rent, proxy bidding, soft close, incumbent bonus, or escalating premium;
- a persistent friend queue, reserved friend place, sponsored faction overflow, Local
  bootstrap exception, or invitation bypass of roster balance;
- monuments, permanent titles, community-vote prestige slots, or prestige currency;
- indefinite Rust-style offline sleepers;
- raw-database cockpit editing or manual choice of a normal auction winner.

The following consequences are intentional and should not be “fixed” with hidden
complexity: one squad member may sell a shared load and distribute money manually;
crystal may remain on a saved character or in a locked safe-zone vehicle; Local
two-city respawn may be used as death travel; offline/inactive faction assignments keep
their current-Vakhta roster places; a friend invite neither guarantees nor reserves a
place; returning fire marks the defender; executing an Aggressor driver leaves the
vehicle moving under ordinary physics with its ACL and cargo intact; ordinary gear moves
between Ugoldar and Kamensk through the one shared module-enabled storage pool; permanent
plot shells survive wipe as empty map infrastructure; a stranded registered vehicle
blocks another instance of that registration until return/loss; a vehicle and crystal
cargo may persist longer in a busy protected city because normal GC is proximity-
sensitive; abandoned vehicle cargo is not recovered; Garrison equipment and money-
transfer abuse relies on whitelist enforcement and audit; physical player trades permit
scams; the in-game leaderboard is cleared completely at wipe after an optional simple
export.
